# 005 — deploy.sh·sync_to_srv.sh 본문을 main() 으로 감싼다

2026-10-13 · `work/20261013-paleoadmin` · paleoadmin

## 왜

DiaRUGA 와 같은 고침(DiaRUGA 221). ForGIA 에서는 아직 터지지 않았지만 구조가 글자 그대로 같다. 거기서는 10-08 v0.32.5 배포(DiaRUGA 220)에서 `deploy.sh` 가 health 게이트를 지난 뒤 **문법 오류로 멈췄다.** 판은 올라갔지만 smoke 는 손으로 돌렸고 9) 옛 이미지 정리(DiaRUGA 219, ForGIA 004)는 안 돌았다.

bash 는 스크립트를 한 번에 다 읽지 않고 도는 대로 읽어 나간다. 그런데 8) 단계 `sync_to_srv.sh --from-image` 가 `/srv/ForGIA/bin/deploy.sh` — 지금 돌고 있는 바로 그 파일 — 를 `cp` 로 **제자리에서** 덮어쓴다(같은 inode). 내용이 같으면 아무 일 없지만, DiaRUGA 219 처럼 `deploy.sh` 가 바뀐 판을 처음 내보내는 배포에서는 bash 가 읽던 바이트 자리가 새 파일의 엉뚱한 곳을 가리킨다. `sync_to_srv.sh` 도 자기 자신(`bin/sync_to_srv.sh`)을 같은 식으로 덮어쓴다.

## 무엇을

두 스크립트 모두 `set -euo pipefail` 다음부터 끝까지를 `main() { … }` 으로 감싸고 맨 끝에서 `main "$@"` 을 부른다. bash 는 함수 정의를 닫는 `}` 까지 다 읽어야 실행을 시작하므로, 도는 동안 파일이 바뀌어도 이미 읽어 둔 본문으로 끝까지 간다.

- 들여쓰기는 일부러 안 했다 — 본문 diff 를 깨끗하게 두려고. 이유는 스크립트 머리 주석에 적었다.
- 함수 안이라도 `exit`·`trap … EXIT`·`$0` 은 그대로 뜻이 같다.

## 버린 것

- `put` 을 `cp` 대신 임시 파일 + `mv`(새 inode)로 — 돌던 bash 는 옛 inode 를 계속 읽으므로 이것도 막지만, `/srv` 의 그룹 권한·소유를 `put` 이 지켜 온 방식을 다시 따져야 한다. main 감싸기가 더 작고 스크립트 안에서 끝난다.

## 확인

`bash -n` 통과. 같은 꼴의 작은 스크립트로 돌다가 자기를 `cp` 로 덮어쓰게 해 보니, 감싸지 않은 쪽은 덮어쓴 직후 조용히 멈췄고 감싼 쪽은 끝까지 돌았다.

**이 고침도 처음 한 번은 못 막는다** — 지금 `/srv/ForGIA/bin/deploy.sh` 는 감싸지 않은 판이라, 이 변경이 실린 판을 내보내는 첫 배포에서는 8) 단계 뒤가 또 어긋날 수 있다(판은 이미 올라간 뒤다). 그 배포는 `sync_to_srv.sh` 를 먼저 손으로 돌려 `/srv/bin` 을 바꿔 두고 배포하거나, 멈추면 smoke·정리를 손으로 돌린다. 그 다음부터는 막힌다.
